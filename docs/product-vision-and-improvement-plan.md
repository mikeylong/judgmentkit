# JudgmentKit product vision and improvement plan

JudgmentKit's purpose is to help people build useful interfaces with AI agents. Mike selected that direction for this review. The improvement plan starts by defining what useful means to the builder and the eventual user, then tests which parts of JudgmentKit help reach that outcome.

Proposed vision: **JudgmentKit helps a person and their AI agent turn an intent into an interface that makes the intended work easier.**

Proposed product promise: the agent understands the work, makes consequential design choices visible, and receives specific corrections when the result fails the intended activity. Successful use leaves the builder with a working interface, a clear reason for its structure, and an honest account of what was checked and what remains unresolved. The eventual user can complete a representative task correctly. Usefulness includes reliable interactions, readable and appropriate presentation, and accessible completion of essential paths.

The vision and product promise are proposed outcomes, not established performance claims. The plan follows [DESIGN.md](../DESIGN.md), the [kernel spec](../specs/judgmentkit-kernel.md), and the [AI UI generation contract](../contracts/ai-ui-generation.activity-contract.json). It replaces the [chart-first proposal](chart-verification-and-evidence-preflight-plan.md) as the recommended roadmap. Existing implementation changes and regression evidence remain intact.

The primary user is a hands-on builder directing an AI agent to create or improve an interface. The agent operates JudgmentKit; the builder makes product decisions. The eventual interface user benefits from the result. An organizational buyer, willingness to pay, and repeat adoption remain open research questions.

The candidate job is: when an agent's first draft requires repeated correction or makes the wrong work easy, help the builder reach an interface that someone can use without personally translating every product decision into implementation instructions. Possible benefits include less rework, easier assessment of the result, and a handoff the builder can explain. Possible reasons to reject JudgmentKit include setup effort, unnecessary stops, unwanted design-system constraints, or no improvement over the builder's usual agent. Recent builder episodes must establish which of these hypotheses matter.

The product review remains at the hypothesis level. The inspected sources demonstrate contracts, examples, and bounded comparisons. They do not establish current adoption, repeat value, or superior task completion. The archived pilot disagreement is a reason to investigate evaluation validity, not a verdict on today's implementation.

1. **High: agree on a focused vision and completion condition.** Draft a short vision proposal covering the starting builder, the struggling moment, the intended progress, and the job JudgmentKit owns. Review the homepage, README, kernel spec, portable skill, and first-use material against that proposal. Distinguish deciding what to build, guiding a build, and improving an existing interface as entries into the same builder job. Decide which entry should lead based on recent use episodes.

   Preserve activity fit, domain language, succinct interaction, and disclosure discipline. Treat patterns as guidance derived from the work, including cases that combine purposes. Keep components, team standards, and evaluation infrastructure subordinate to the builder outcome. Define three honest capability levels: JudgmentKit can guide a decision, check a declared requirement, or verify a supported behavior. Each level needs its own evidence.

   Deliver a proposed vision document, a claim-to-evidence map, and a short list of deliberate exclusions. Completion means Mike can explain who JudgmentKit helps, the result that person gets, and why that result warrants using it alongside their agent.

2. **High: test the smallest complete builder experience.** Use the existing portable skill and runtime to prototype one path: describe or show the work, correct a short working premise, build or revise the interface, inspect the important tasks, and apply focused repairs. The agent should handle packet assembly and tool selection. The builder should see the interface, consequential choices, and the changes that matter.

   Preserve authoritative-source requirements and existing acceptance boundaries. Show reversible assumptions without turning them into an interview. Make the premise correctable during iteration. Route unusual or mixed activities through an explicit explanation rather than forcing a familiar pattern. Keep full diagnostics available on request. Avoid introducing a new orchestration service before observing whether the existing skill can deliver this experience.

   The first learning encounter needs one builder with a recent real interface task, their normal agent workflow, and a person able to perform the resulting interface's target activity. Observe a complete episode, including setup and repairs. Compare against a matched task using the builder's usual approach, counterbalancing order where possible. Record task differences and learning effects. Failure means the builder cannot reach the agreed result, works around JudgmentKit, or the resulting interface fails the target task. Treat one encounter as a learning test, not an efficacy claim.

3. **High: evaluate usefulness across contrasting activities.** After the first encounter, expand to a small qualitative pilot: at least three builders and three task types, including an ordinary form, an improvement to an existing workbench, and a read-only information interface. Select fresh inputs before running the experiment. Use the nine surface patterns as coverage vocabulary; do not make equal coverage of all nine a prerequisite for learning. Tide remains one regression fixture.

   Compare three conditions: a capable agent with ordinary instructions, the same agent with concise activity-first guidance, and the full JudgmentKit path. Hold the brief, source data, model settings, implementation system, underlying build/test tools, and budget policy constant within each task comparison. JudgmentKit's tools are part of the treatment. Include both total overhead and a matched generation budget so extra computation is visible.

   Cap the initial round at nine observed build episodes: three task types across three conditions. Rotate conditions across builders and counterbalance order so no builder repeatedly solves the same task. Record builder experience as a possible confound. Independently assess all nine resulting artifacts with representative end-user tasks and hidden treatment labels. Retain failures and abandoned episodes. Expand with repeated runs only after this round identifies a product decision that needs more evidence. Task completion must be observed rather than inferred from labels or screenshots.

   Reuse the [existing comparison protocol](standalone-comparison-experiment.md). Measure builder time to a usable result, manual corrections, false stops, unnecessary questions, review attempts, and setup effort. Separately measure correct task completion, comprehension, interaction failures, and accessibility for the required paths. Ask builders to bring a subsequent task; observed return use provides stronger evidence than stated interest. Keep automated contract tests as engineering evidence and model preference as supporting evidence.

   Before running the pilot, record task-specific success criteria and each builder's tolerable overhead. Continue if JudgmentKit improves correct completion or reduces correction effort across contrasting tasks within those limits. Simplify if concise guidance captures the value and the full workflow adds cost. Concentrated value in one activity or in critique suggests a narrower initial offer. If neither path improves the result, reconsider the promise. A small pilot selects the next learning step; it cannot establish market-wide superiority.

4. **High: implement only improvements that the pilot supports.** Rank observed failures by their effect on builder progress and end-user success. Packet errors suggest evidence preflight; routing failures suggest stronger semantic interpretation and explanations; accepted-but-unusable results suggest a specific runtime check. Establish recurrence or a material consequence before selecting those investments. Authority or accessibility defects can warrant a fix without waiting for frequency evidence.

   For every change, state the failure, the expected benefit, the behavior-level test, and the outcome check. Follow [the testing skill](../skills/write-tests/SKILL.md). Validate changed contracts and affected adapters, then use proportional integration checks. Chart verification, interactive attestation, additional patterns, component expansion, and reusable project judgment remain candidates until their contribution is established. Avoid treating more checks or more contract coverage as the success measure.

5. **Medium: align the public product with the demonstrated experience.** Retain the homepage's clear activity-first promise, then give visitors one obvious way to try the complete builder loop. Draft a first-use walkthrough using a real brief, a working result, a focused repair, and explicit verification limits. Place integration schemas and diagnostic fixtures in supporting documentation. Let the design system remain an available implementation choice.

   Update the homepage, value page, docs, examples, README, and portable adapters together when the proposed experience works. Label examples by evidence type: curated fixture, generated artifact, observed task, or repeated use. Make historical eval dates and capability limits easy to understand. Measure whether a new builder can connect their agent and complete the first task without help. Public edits and release work are subsequent implementation tasks; this plan changes no hosted behavior.

The sequence is vision proposal, one real builder encounter, a contrasting-task pilot, focused product improvements, and a demonstrated first-use path. The immediate deliverable is a clearer product decision and a testable builder experience. Specialized verification follows the evidence from that experience.
