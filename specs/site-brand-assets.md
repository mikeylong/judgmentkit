# JudgmentKit website identity

Browser tabs, saved shortcuts, installed apps and shared links use the approved Slab J and outlined Inter 780 wordmark. `site/brand-assets.json` records the website contract; `scripts/build-site-brand-assets.py` produces its deterministic exports. Canonical lockups, mark polygons, native icon masters, header/footer markup, navigation and page copy remain unchanged.

Browser icons use a transparent 64 × 64 canvas, with no plate or corner radius. The visible mark is 48 units high and its actual ink bounds center on (32,32). Light uses Ink `#0B0D0E` primary polygons; dark uses Ivory `#F7F6F2`. The return stays Nickel `#8B9096`. A single external uniform transform places the supplied polygons. The approved optical derivative remains available at 16px with a 12px visible height; the canonical polygons govern 32px and larger views. Each theme has a 16px/32px/48px ICO whose decoded frames exactly match its transparent PNG exports.

Every managed HTML head runs the shared `site/assets/brand/favicon-theme.js` controller as a synchronous external classic script. The controller selects the light or dark ICO using `matchMedia` before appending exactly one typed `rel="icon"` link. It updates that same link when the scheme changes. No other static SVG, PNG or ICO favicon links compete. A `<noscript>` link supplies the light ICO only when scripting is disabled. The controller, its two themed ICO paths and the other identity assets use the content-derived bundle key; controller bytes participate in that key. The SVG and PNG assets remain served for compatibility and explicit rendering checks.

Legacy `/favicon.svg`, `/favicon.ico` and PNG aliases return current transparent dark artwork. Safari pinned tabs use the canonical single-color silhouette without a plate because the platform supplies its tint. Native Safari fixture checks established readable transparent Ink/Nickel in light appearance and transparent Ivory/Nickel in dark appearance. An existing Safari origin can retain its previously processed favicon; current source, a new URL or a successful image probe does not establish the state of that cache. Scheme-change DOM updates likewise do not alone prove native toolbar refresh.

Apple touch and regular PWA icons use the same 48-unit placement on an opaque square Ink plate with Ivory primary polygons and Nickel return. Platform masks provide rounding. Maskable icons use the same dark treatment at a documented 36-unit visible-height alternate, centered on (32,32), to keep every vertex inside the central 80%-diameter safe circle. This changes only placement and colors, preserving all canonical polygon coordinates. The manifest background is Ink; `id`, `start_url` and `scope` remain `/`; no service worker is introduced.

Sharing art is an opaque 1200 × 630 Ink canvas containing the complete reversed lockup at `min(2.8,960/viewBoxWidth)`, centered by its full viewBox. The sharing image has no tagline, title panel, rounded frame or separately typed wordmark. The product title, description and domain belong to native preview metadata. Open Graph, Twitter and `image_src` use a SHA256-derived PNG URL. The previous July and October sharing URLs and the unversioned PNG/SVG aliases return current artwork.

`site/brand-assets.mjs` copies exports byte for byte and applies the managed identity entries to shared pages and copied reports, examples and experiments. It preserves every body byte, page title, description, canonical URL and existing social context such as article type, locale, video metadata and creator. The sole exception remains `/assets/releases/visual-composition-runtime-demo.html`, an immutable noindex recording source with a data-only image CSP and empty `data:,` favicon.

Icon, touch, pinned-tab and manifest filenames include a shared SHA256-derived key. The key covers all content-versioned icon and controller source bytes and the complete logical manifest. New bytes produce new URLs while compatibility aliases and installed-app identity remain stable. Current HTTP bytes and a fresh browser do not establish the state of an existing Safari favicon/history cache.

`legacy_icon_aliases` retains the 39 published icon, touch, app and manifest URLs from bundles `2cbf1750a49bf439`, `86b6a01d9795231a` and `cfee0c66322f931c`. Each explicit route serves its current equivalent asset; older manifests serve the current manifest with stable `/` app identity. These compatibility routes do not enter the new bundle hash or page heads. Add only recorded published paths, without a catch-all rule for arbitrary hashes. Keeping a remembered URL available permits revalidation; it does not prove that Safari has refreshed its cached icon or removed browser-drawn framing.

Regenerate with `python3 scripts/build-site-brand-assets.py`, using ImageMagick and Pillow. Icon rasterization uses `magick -background none -density 384 input.svg -resize target! -strip -colorspace sRGB PNG32:output.png`, with `PNG24` for opaque platform icons. Social art retains density 192. No installed font is required. Normal Node builds copy committed exports without those rendering tools. Run `node tests/site.test.mjs` and `node tests/site-brand-assets.test.mjs`, then inspect actual 16px/32px browser renders in both schemes, Apple/PWA/maskable placements and the complete sharing PNG. Run `node tests/site-favicon-browser.test.mjs` for real Chromium initial selection, theme updates, no-script fallback and one-icon cardinality. Native Safari checks remain separate from headless browser coverage. Explicit image/canvas probes do not prove native favicon selection.
